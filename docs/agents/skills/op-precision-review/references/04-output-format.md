# 检视意见输出格式

## 1. 单条意见格式

沿用仓库代码检视输出规范（见根 `AGENTS.md`「代码检视输出规范」），并在其中补两行精度检视字段：

```text
【review】
问题分类：<编码红线问题|cleancode|兼容性问题|性能问题|测试问题>
精度级别：<lv0|lv1|lv2|lv3>
细粒度根因：<同步/事件时序|越界/地址偏移|dtype/format|tiling/分核错误|shape/校验缺失|模板/分支缺失|内存容量/超限|索引/计数|NaN/Inf/除0|空值/null|数值溢出/位宽|累加顺序/舍入|bias/辅助输入|责任田补充根因>
位置：path/to/file.cpp:123，代码：xxx
问题：<具体变量、函数、分支或逻辑哪里不符合预期>
可能导致的结果：<触发条件 + 影响；不要只写"可能有问题">
建议的修改方法：<可执行的修改方向>
```

字段要求：

1. `问题分类` 取仓库现有的五个分类；精度类问题通常落在 `编码红线问题`，只有当根因本身是
   平台/版本差异时才是 `兼容性问题`。分类与本 skill 的"精度级别"是两套坐标，不能互相替代。
2. `精度级别` 按 [`01-scope-and-categories.md`](01-scope-and-categories.md) §3 的判据选择：判据来自 scalar 逻辑 → lv0；
   来自接口文档 → lv1；来自 AscendC API/硬件手册 → lv2；来自分核/内存/同步方案 → lv3。
3. `细粒度根因` 只填一个主根因；同一处有多个根因时，主根因决定级别，其余在"问题"里用一句话带出。
4. `位置` 必须给文件名与行号；代码片段只截取能说明问题的最短一段。同一根因出现在多个文件时逐个列出。
5. `可能导致的结果` 必须写触发条件（shape、dtype、layout、属性、分支、SoC）与后果
   （结果错、精度劣化、越界、超时、崩溃、接口语义错误），并区分"必然发生"和"特定条件下发生"。
6. `建议的修改方法` 给方向而不是整段补丁；涉及同步/内存时要点明需要保护的依赖类型与资源。

## 2. 额外发现

不在已知 issue 列表中但确实存在的问题，按同一格式输出，并在"问题"结尾追加：

```text
（额外发现）
```

额外发现要保留：验收时它既可能是有效 bonus，也可能是虚警，由人工判定，不能因为"issue 里没写"而丢弃。

## 3. 材料不足

缺少判定材料时写成：

```text
【review】
问题分类：编码红线问题
精度级别：lv3
细粒度根因：同步/事件时序
位置：path/to/file.cpp:200，代码：CrossCoreWaitFlag(flagId)
问题：缺少该算子的流水详设与 flag 分配表，无法判定 flagId 的 set/wait 是否成对，也无法确认参与核数。
可能导致的结果：若参与核数与 flag 深度不匹配，可能出现计数器错位或 kernel 超时。
建议的修改方法：补充 flag 分配表（生产者、消费者、方向、复用深度）后重新检视该处；在此之前不作为已确认问题统计。
```

不得用"看起来没问题""应该是对的"代替结论，也不得为了凑数量把材料不足写成确认问题。

## 4. 汇总（可选）

需要给出检视概览时（例如提交检视报告），在意见列表之后附一张分布表，不写"整体没问题"这类总评：

| 精度级别 | 意见数 | 分布（按细粒度根因） |
| --- | --- | --- |
| lv0 | n | 索引/计数 2、空值/null 1 |
| lv1 | n | shape/校验缺失 3 |
| lv2 | n | 越界/地址偏移 1 |
| lv3 | n | 同步/事件时序 2 |

## 5. 示例

```text
【review】
问题分类：编码红线问题
精度级别：lv0
细粒度根因：空值/null
位置：fla/ops/ascendc/kda/chunk_kda_fwd/op_host/chunk_kda_fwd_tiling.cpp:418，代码：const auto totalTokens = cuSeqlens->GetData()[seqCount];
问题：rank-4 变长输入的 cu_seqlens 允许 B 或某个序列长度为 0，取最后一个元素作为 totalTokens 前没有校验
      序列数非 0、末尾元素与输入 token 数一致，空序列场景下 totalTokens 取到未初始化或 0 值继续进入分核计算。
可能导致的结果：空序列或 B=0 的输入不会在参数校验阶段返回 ACLNN_ERR_PARAM_INVALID，而是把 0 token 的序列
              交给 tiling，出现除零或空 workspace 访问，表现为缺少上下文的硬件错误码。
建议的修改方法：在参数校验阶段拦截 B/序列长度为 0 的输入并给出明确报错；同时校验 cu_seqlens 首元素为 0、
              末尾元素等于总 token 数、整体单调不减，与文档中的约束条目保持一致。
```

```text
【review】
问题分类：编码红线问题
精度级别：lv0
细粒度根因：索引/计数
位置：fla/ops/ascendc/kda/chunk_kda_fwd/op_kernel/arch35/chunk_kda_fwd_prepare.h:266，代码：for_k = chunkStart; for_k < chunkStart + blockK; ++for_k)
问题：尾 chunk 的分块循环用 blockK 作为固定上界，没有按 min(blockK, validRows - chunkStart) 裁剪，
      当 chunk 不足一个 block 时会读到相邻 chunk 的行。
可能导致的结果：尾块或 varlen 短序列下把下一个 chunk 的数据算进当前结果，精度在长尾序列上随机劣化，
              小 shape 用例不易复现。
建议的修改方法：把循环上界改为按实测有效长度裁剪，或对无效行写入中性值并在后续计算中遮罩；
              同时补充一个 chunk 不足一 block 的边界用例。
```
