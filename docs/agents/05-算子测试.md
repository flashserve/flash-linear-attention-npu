# 算子测试

本阶段以已确认的接口、CPU 标杆和算子设计为依据，选择与改动相匹配的验证路线，
确认实现满足交付要求。单算子用例、执行方式和结果记录统一参见
[`tests/atk/README.md`](../../tests/atk/README.md)，具体算子的范围参见其 ATK README。
接口、CPU 标杆、输入生成器、混合容差或覆盖场景变化时，先按精度文档的
[`值域校准`](reference/精度对比与定位.md#值域校准)确认规则，再进入 ATK 执行。

## 阶段输入

- 算子目录中的 `docs/api.md` 和 `docs/design.md`，以及存在时的开发期 `docs/validation.md`。
- 已确认的独立 CPU 标杆、输入生成方式和比较标准。
- 与当前接口、CPU 标杆、输入生成器和混合容差一致的值域校准记录。
- 当前实现、目标分支 diff 和受影响文件列表。
- 接口或功能修改的差异清单、修改前行为和原有场景回归范围。
- 存在性能目标时，用户提供的模型 case、对比基线、逐 case 目标和统计方式。

## 验证路由

| 改动场景 | 必须执行的验证 |
| --- | --- |
| 仅修改文档 | 检查格式、链接、命令及文档与代码是否一致 |
| 仅修改 ATK JSON/YAML、generator、executor 或测试脚本 | 检查语法和导入，执行修改后的测试入口；输入生成、值域、混合容差或覆盖场景变化时重新校准并正式验收 |
| 修改 CPU 标杆或预期结果 | 返回阶段 2 更新并验收 CPU 标杆、校准值域，再重新检查并执行阶段 3 → 4 → 5 |
| 新增算子或修改算子私有实现 | 构建当前代码并完成受影响算子的单算子验证 |
| 修改接口、功能或支持范围 | 完成单算子验证；验证新增或变化的正常、边界和异常场景；回归声明不变的原有场景 |
| 修改 TilingKey、模板选择或运行时分支 | 完成单算子验证，并提供全部可达 key 和分支的实际选择证据 |
| 修改性能策略、Stage、流水、资源或 workspace | 完成单算子验证；在相同条件下比较优化前后性能；确认目标场景达到预期，其他支持场景无不可接受的下降 |
| 修改公共组件、ABI、代码生成模板或 runtime | 验证全部受影响算子，并直接验证被修改的公共逻辑；影响公开调用时补充公开入口和安装验证 |
| 修改公开接口、打包或安装行为 | 验证 ABI、Python/torch 入口、动态库、OPP、重复安装和必要的 Example/ST |
| 修改 GDN 端到端链路 | 完成受影响算子的单算子验证和 Example/ST |

一项改动命中多行时，合并执行对应验证。单算子验证的用例、命令、执行阶段和结果记录统一按
[`tests/atk/README.md`](../../tests/atk/README.md) 执行。公共改动沿引用、代码生成和调用关系
列出全部受影响算子；无法确认的影响范围记录依据和风险。

凡验证路线包含单算子验证，必须按 [`tests/atk/README.md`](../../tests/atk/README.md) 完成用例准备、
覆盖确认和正式验收；未满足其中任一完成条件时，不得归档测试结论或完成本阶段。

验收发现精度不一致时，进入
[`精度对比与定位.md`](reference/精度对比与定位.md#算子实现定位) 的“算子实现定位”选择采数和分析方法；根据
定位结论返回最早受影响阶段修正。修复并通过逐 Stage 和整算子精度检查后，按原验证路由重新验收。

## 归档与完成条件

测试结果按 [`tests/atk/README.md`](../../tests/atk/README.md) 规定归档到当前算子的 ATK README。
存在 `docs/validation.md` 时，将仍有效的覆盖范围、测试版本、通过结果和性能结论收敛到最终记录，
删除该开发期文件及所有指向它的链接。

本阶段完成需要同时满足：

- 每个受影响算子均已满足 `tests/atk/README.md` 的正式验收条件。
- 验证路由中的其它必测项均已完成。
- 存在性能目标时，每个模型 case 均已在固定条件下实测，并逐项与目标比较；
  任一 case 未测试或未达标时，整体结论为未达标，除非用户明确接受该差异。
- 接口、CPU 标杆、设计、实现和测试结果一致；公共改动涉及的每个算子均已验证。
- 最终结论已归档，开发期验证记录已删除。
