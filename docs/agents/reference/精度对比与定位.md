# 精度对比与定位

本文件是精度对比、值域校准和问题定位的统一入口，同时维护场景路由、判断规则和通用执行方法。
阶段 2 使用“标杆对齐”，阶段 4 和阶段 5 出现精度不一致时使用“算子实现定位”。测试环境准备和
正式验收命令在 [`tests/atk/README.md`](../../../tests/atk/README.md) 维护；精度失败后的输出采集和
分析方法在本文件维护。

值域由接口、CPU 标杆、输入生成器和混合容差确定，不随算子实现变化。上述基线或覆盖场景变化时
重新校准；其余代码修改使用已固化值域验证。

## 场景路由

| 触发场景 | 定位路线 | 执行入口 | 处理后的阶段 |
| --- | --- | --- | --- |
| 参考实现与 CPU 标杆结果不一致 | [`标杆对齐`](#标杆对齐) | 同章节的采数、混合容差和 CT 步骤 | 阶段 1 或阶段 2 |
| 精度基线变化，或新增原值域未覆盖的场景 | [`值域校准`](#值域校准) | 更新并固化值域 | 阶段 2 |
| NPU 整算子与 CPU 预期不一致 | [`算子实现定位`](#算子实现定位) | [`整算子精度失败复现与输出采集`](#整算子精度失败复现与输出采集) | 阶段 1、2、3、4 或测试 |
| 无法确定首个错误 Stage | [`算子实现定位`](#算子实现定位) | [`Stage 中间结果采集`](#stage-中间结果采集) | 阶段 3 或阶段 4 |
| 差异只出现在 padding 或无效区 | [`共同准备`](#共同准备) | 核对两个实现的有效区域和 mask 规则 | 阶段 1、2 或测试 |

进入任一路线前先完成 [`共同准备`](#共同准备)。处理后返回触发阶段；如果结论改变了更早阶段的
接口、CPU 标杆或设计，则从最早受影响阶段重新执行。

## 共同准备

统一使用 [CT Tool v0.9.1](https://gitcode.com/Wei_NaChuan/ct/releases/v0.9.1)。从发布页安装
`ct_tool-0.9.1-py3-none-any.whl`，并使用 `ct --version` 确认版本。

1. 固定被比较代码、输入、shape、dtype、layout、属性、随机种子、执行次数、有效区域和混合容差。
2. 每个输出分别保存待测结果和预期结果；文件名应包含用例、输出名称、实现角色和随机种子。
3. 最终输出和 Stage 中间结果使用 `.npy`、`.pt` 或 `.pth`，并确保两个实现保存的是相同语义、
   shape 和有效区域的数据；padding 和无效区不参与比较。
4. 对每个输出分别记录比较指标和阈值依据。多个输出必须逐一执行并分别记录，不能用一个输出的
   结果代表整个接口。
5. 记录数据生成命令、比较命令、输入版本、CT Tool 版本和结论。临时数据和内部路径不写入公开记录。

## 值域校准

正式精度比较前，先确认输入值域能够区分正确结果和代表性错误。已确认的混合容差是标杆对齐和
算子验收的唯一 PASS/FAIL 标准。

1. 固定 shape、分支、随机种子、有效区域和混合容差，由小到大调整输入值域并生成候选输入。
2. 对每档值域生成 CPU 标杆、已确认参考实现（如有）和代表性错误输出；错误应匹配当前公式和
   数据流，例如全零、遗漏计算项、错误 scale 或错误 head/chunk 映射。
3. 使用相同的 `rtol` 和 `atol`，确认正确结果通过、代表性错误失败。
4. 分别查看正确结果和代表性错误结果的全值域分布、误差分布、空间位置及 `Inf/NaN`：

```bash
ct viz <correct_output> <golden_output> \
  --out_dir <output_dir> --name <range_name>_correct --spatial

ct viz <representative_wrong_output> <golden_output> \
  --out_dir <output_dir> --name <range_name>_wrong --spatial
```

合适的值域应使正确结果贴近 `y=x`、误差集中在零附近且没有按 head/chunk 或连续区域聚集，同时
使代表性错误与正确结果清晰分离。排除会使合法计算出现溢出、下溢、饱和、非有限值或超过既定
数值误差的值域，在剩余候选中选择能稳定暴露代表性错误的最小值域。

将选定值域固定到输入生成器。开发期在 `docs/validation.md` 记录接口、CPU 标杆、输入生成器和
混合容差版本，以及候选值域、正确和错误结果与最终选择；正式验收不临时放宽标准。

## 标杆对齐

比较用户参考实现与独立 CPU 标杆时，使用同一份已保存输入分别运行两个实现，不允许各自重新
生成随机输入。执行命令由各自调用说明提供，并在阶段 2 的对齐记录中保存，例如：

```bash
python <reference_runner> --input <input_file> --output <reference_output>
python <cpu_runner> --input <input_file> --output <cpu_output>
```

1. 先使用结果可人工检查的最小用例确认公式、返回顺序和有效区域，再运行阶段 2 的完整对齐用例。
2. 按 [`值域校准`](#值域校准) 选定输入范围，使用已确认的 `rtol` 和 `atol` 对每个有效输出执行
   混合容差判断：

```python
torch.testing.assert_close(
    cpu_output,
    reference_output,
    rtol=confirmed_rtol,
    atol=confirmed_atol,
    equal_nan=False,
)
```

3. 混合容差未通过时，查看误差分布、空间位置和 `Inf/NaN`，判断差异来自公式、计算顺序、dtype、
   无效区还是阈值：

```bash
ct viz <cpu_output> <reference_output> \
  --out_dir <output_dir> --name <case_name> --spatial
```

4. 接口未定义的差异返回阶段 1 确认；CPU 标杆有误时在阶段 2 修正。全部差异解决后才能进入阶段 3。

## 算子实现定位

单 Stage 或整算子的 NPU 结果与 CPU 预期不一致时：

1. 先按 [`整算子精度失败复现与输出采集`](#整算子精度失败复现与输出采集) 固定失败用例并保存输出，
   使用原混合容差复现问题。
2. 按计算顺序比较最终输出和已有 Stage 中间结果；无法确定首个错误 Stage 时，按
   [`Stage 中间结果采集`](#stage-中间结果采集) 从 Stage 0 开始定位第一次出现差异的位置。
3. 按原因处理：接口或支持范围不明确时返回阶段 1；CPU 标杆有误时返回阶段 2；设计有误时返回
   阶段 3；计算、同步、搬运、数据排布或写回实现有误时修复阶段 4 代码；测试文件或比较方式有误
   时修正对应测试。
4. 修复后使用相同条件，从最早受影响的 Stage 重新验证到当前目标；全部通过后才能继续开发。

## 整算子精度失败复现与输出采集

先读取 ATK README 的 [`运行前准备`](../../../tests/atk/README.md#运行前准备) 和当前算子的 ATK
README，确认测试文件、CPU 标杆、算子入口和构建结果一致。先通过 ATK README 的
[`全量精度执行`](../../../tests/atk/README.md#全量精度执行) 复现失败。

需要固定失败用例并保存 NPU/CPU 输出时，在当前算子的 ATK 目录执行：

```bash
cd tests/atk/<op_name>
atk node --name npu_dut --backend npu --devices <device_id> \
    --output_path <output_dir> \
  node --name cpu_golden --backend cpu \
    --output_path <output_dir> \
  task \
    -c ./atk_<op_name>.json \
    --task accuracy \
    --bm_device cpu \
    -p ./executor_<op_name>.py \
    -s <case_id> \
    -e <case_id_plus_one> \
    --save_data output \
    --gm_init_flag \
    -to <timeout>
```

`-e` 不包含在执行范围内，单用例应设置为 `case_id + 1`。输出保存后，先从 ATK 报告确认实际
执行的 case id、seed、输出名称和精度结果。

采数后先核对输出名称、shape、dtype 和有效区域，再使用原混合容差复现失败。需要观察空间误差时
执行：

```bash
ct viz <npu_output> <cpu_output> \
  --out_dir <output_dir> --name <case_name> --spatial
```

## Stage 中间结果采集

阶段 3 必须在当前算子的 `docs/validation.md` 中为每个 Stage 记录以下内容：

| 项目 | 必须记录的内容 |
| --- | --- |
| DUT 采集 | 构建命令、运行命令、Stage 输出位置、shape 和 dtype |
| golden 生成 | CPU 标杆入口、相同计算顺序、输出位置、shape 和 dtype |
| 比较范围 | 有效区域、mask/padding 规则、`rtol` 和 `atol` |
| 成功条件 | 混合容差通过，且没有 `Inf/NaN` |

定位时按 `docs/validation.md` 中已经评审的命令执行，不在定位阶段临时设计采数方法。从 Stage 0
开始依次比较，找到首个不一致 Stage 后停止扩大范围，并对该 Stage 执行混合容差判断和 CT
可视化。采数方式、Stage 公式或计算顺序本身有误时，返回阶段 3 修正文档并重新评审。
