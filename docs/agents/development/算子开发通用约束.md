# 算子开发通用约束

本文是新增、修改、优化或检视算子前必须阅读的前置约束，覆盖 Ascend C、host tiling、aclnn、Python 适配、Triton、wheel、OPP、测试和文档。根 [`AGENTS.md`](../../../AGENTS.md) 是仓库强制规则的最高入口；本文补充跨层开发约束，具体实现细节分别以 [`算子编码规范.md`](算子编码规范.md)、[`验证方法与矩阵.md`](验证方法与矩阵.md) 和 [`算子开发交付清单.md`](算子开发交付清单.md) 为准。

## 设计先行与算子目录归档

新增、融合、重构或较大范围优化 Ascend C 算子时，必须在写实现代码前先完成并归档具体设计文档：

- 固定位置为 `fla/ops/ascendc/.../<operator>/docs/算子开发设计.md`。如果算子目录没有 `docs/`，先创建该目录；设计文档与算子实现、README、aclnn 文档和测试资产一起维护。
- 文档必须参考 [`算子开发设计文档模板.md`](算子开发设计文档模板.md) 和仓内归档的 [`GDN backward finalize 全融合 Ascend C 算子设计`](../../../fla/ops/ascendc/gdn/chunk_gdn_bwd/chunk_gdn_bwd_finalize/docs/算子开发设计.md)，并采用其完整设计顺序：目标与范围、接口、数学语义、依赖和 stage、L1/UB/workspace 生命周期与容量、tiling/构建、测试、性能、风险和迭代记录。
- 参考只约束设计结构和证据类型。参考设计中的具体 shape、SOC、stage 编号、head window、slot、容量、同步编号和固定路径不得直接复制，必须根据当前算子的语义、支持范围和硬件资源重新推导。
- 设计文档必须列出所有既有输入、可选输入、属性和外部元数据的来源。融合不得删除“可以重新推导”的已有输入；`cu_seqlens`、`chunk_indices` 等已有索引映射必须继续从外部传入并由 host tiling 校验、解析和下发。
- 设计文档完成后才能开始 kernel、tiling、op_api、Python 适配或测试实现。已有算子若没有设计文档，先补文档；修改设计边界时先更新文档，再更新代码和测试。
- 仅修改文档、测试或构建配置，且不改变算子实现、接口、支持范围和执行图时，可以在 PR 中将本门禁标记为不适用，并说明理由；除此之外不能以“只是优化”或“只改测试”为由跳过设计文档。

## 文档和代码必须双向一致

文档里写“不支持”“仅支持”“必传”“预留参数不支持非空”等约束时，代码应有对应拦截；代码新增或收紧拦截时，文档应有同等语义说明。

检查时要双向走一遍：从文档逐条找代码拦截，从代码新增拦截逐条找文档说明。

## ABI 变更要显式说明

修改 `*_def.cpp`、`aclnn_*.h/.cpp`、PyTorch schema、ctypes 声明或 opapi 适配代码前，必须逐项核对公开接口和 ABI。不得改变既有参数名称、数量、顺序、类型、默认值和语义。确需演进时优先新增独立 V2 接口，并同步代码、schema、ctypes、文档和测试；PR 必须说明影响范围、兼容策略、迁移方式和回归范围，并按 `.github/CODEOWNERS` 请求对应 owner 检视。

## 融合保持输入契约和信息来源

融合优化只改变执行图、kernel 阶段、中间量位置和生命周期，不得顺带重构既有输入契约或改变信息来源。

- 融合前已有的输入、可选输入、属性和外部元数据必须保持名称、顺序、dtype、layout、默认值和既有语义。
- 调用方已持有或原调用链已显式提供的信息必须继续从外部传入。`cu_seqlens`、`chunk_indices` 及其他既有索引映射只能由 host tiling 校验、解析和下发，不得为了减少 L0 参数而在 host tiling 或 kernel 内根据其他输入重新生成。
- 合并多个旧阶段时，设计文档应逐项列出新入口参数对应的原来源，证明没有丢失输入、改变可选关系或把外部信息变成内部假设。
- 只有原接口未提供、且不承载算子语义的新增实现信息，例如 core 分配、tile、head window、workspace offset 和模板选择，才由 host tiling、tiling data 或编译期模板参数推导。

参数是否“可以推导”不能作为删除既有输入的理由。接口精简与融合优化属于两个独立变更，必须分别设计、评审和验证。

## 生成代码不要手改后遗忘来源

`torch_custom/fla_npu` 下部分文件由 YAML 和生成脚本产出。修改前必须追溯文件来源；属于生成结果时，应修改生成输入、生成脚本或模板并重新生成，不得只手改生成结果。确需手改时必须证明该文件不是生成物，或同时修复生成链路，防止下一次生成覆盖改动。

## 旧调用路径只做兼容

新代码、测试和示例必须优先使用 `fla_npu.ops.ascendc` 下的稳定 Python 入口。`torch.ops.npu.*` 只用于兼容旧调用和兼容性验证；新增调用不得默认依赖该路径，确需使用时必须说明稳定入口不可用的原因。

## wheel 公开 import 面只用 fla_npu

一体化 wheel 和 `torch_custom/fla_npu` standalone wheel 的 pip 项目名都应是
`flash-linear-attention-npu`，安装后的公开 import 名只应是 `fla_npu`。不要在
wheel 运行路径里依赖顶层 `fla` 包。

Triton 算子也应通过 `from fla_npu.ops.triton import 算子名` 暴露；如果代码里
出现 `from fla.ops...`，需要确认它只是源码树内部引用，不会进入安装后 wheel
的运行依赖。standalone wheel 只包含 Python 适配和 OPP 骨架，run 包覆盖后的
`site-packages/fla_npu/opp/vendors/fla_npu_transformer` 才是实际 Ascend C 产物入口。

## 功能分支必须前置建模

线性注意力类算子经常同时支持 dense/varlen、多种 layout、不同 head 关系、可选 initial/final state 和特殊 gate 语义。设计阶段必须列出这些分支的支持矩阵、共享路径和差异路径；实现与测试不得只覆盖默认 shape。具体覆盖要求见 [`验证方法与矩阵.md`](验证方法与矩阵.md)。

## ATK 测试资产是开发契约

Ascend C 算子已有 `tests/atk/<op>` 时，开发、优化和问题修复必须同步维护该目录，并以 ATK 精度通过作为一轮迭代完成的前置条件。新增算子应补齐 README、YAML、用例生成器、已评审 JSON 和 executor；修改 TilingKey 或 tiling 分支时还必须维护 TilingKey 到 case 的覆盖矩阵和实际命中证据。旧单算子脚本可以补充 ABI 或兼容性验证，但不能替代已有 ATK 工程。

## head ratio 不要隐式假设为 1

反向和局部梯度算子常见 `H_out`、`H_do` 与 `H_qk` 不相等的场景。实现中必须显式推导并校验 head ratio，用输出 head 映射回 Q/K head；测试必须覆盖 ratio 大于 1。不得隐式假设所有 head 数相等，具体地址和类型要求见 [`算子编码规范.md`](算子编码规范.md)。

## workspace slot 是协议，不只是地址

多阶段 AIC/AIV 算子里，workspace slot 同时承载数据和同步协议。设计时必须定义 slot 的 producer、consumer、地址键、复用顺序、ready/free 和最后消费点；tail、空任务和非 owner 路径也必须配平。不得让 AIV 跳过空任务而 AIC 仍等待，也不得让 AIC 覆盖 AIV 尚未消费的 tile。详细生命周期规则见 [`算子编码规范.md`](算子编码规范.md) 和 [`../optimization/README.md`](../optimization/README.md)。

## 提交前清理产物

构建目录、wheel、run 包、测试输出、profiling 输出、临时 patch、缓存和本地调测脚本不得进入提交。提交前必须执行 [`算子开发交付清单.md`](算子开发交付清单.md)，查看 `git status --short`，确认未跟踪文件中没有生成物或敏感信息。
