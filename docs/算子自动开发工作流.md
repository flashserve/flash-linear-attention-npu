# Ascend C 算子自动开发工作流

本文记录 CANNBot `catlass-cpp-generator` 的 `linear_attention` 功能分支与本仓适配、ATK 和上库
流程之间的边界。CANNBot 五阶段的具体方法以实际使用版本为准。

本仓当前使用 [CANNBot PR 1274](https://gitcode.com/cann/cannbot-skills/pull/1274) 中的
`plugins-official/catlass-op-generator/catlass-cpp-generator`。开始任务时记录实际使用的 commit；
任务恢复时继续使用同一版本，升级前先检查工作流和产物格式。

## 固定路由

本仓 `fla/ops/ascendc/**` 均属于线性 Attention 算子域，直接设置：

```text
algorithm_family=linear_attention
workflow_id=catlass-linear-attention-v1
```

上述字段直接作为算法域分类结论。CANNBot 可用且版本匹配是工作流入口条件；缺少条件时记录并
报告阻塞项。

## 适用范围与进入阶段

新增算子从 CANNBot 01 开始完整执行本工作流。未修改的现有算子不要求批量迁移；现有算子发生
接口、标杆、方案、kernel、host tiling 或性能修改时，从本次变更对应的阶段接入，并按新工作流
完成后续阶段和交付资产。接入时将现有接口、标杆和设计作为当前基线登记，初始化 workflow 状态，
不为形式上的流程完整而重做未受影响的前置阶段。

| 开发场景 | 进入位置 |
| --- | --- |
| 新增算子 | CANNBot 01，完整执行五阶段 |
| 接口、语义或支持范围修改 | CANNBot 01 |
| 标杆、值域或精度策略修改 | CANNBot 02 |
| Stage、tiling、同步或资源方案修改 | CANNBot 03 |
| kernel 或 host tiling 实现问题修复 | CANNBot 04 |
| 不改变设计的性能优化 | CANNBot 05 |
| 涉及设计变化的性能优化 | CANNBot 03 |
| 仅仓库适配层、ATK 资产、测试用例或文档修改 | 不进入 CANNBot 阶段，按对应仓库规则验证 |

## 执行顺序

```text
CANNBot 01：冻结接口和 operator contract
  -> CANNBot 02：生成唯一 CPU 标杆和 precision policy
  -> CANNBot 03：完成 Stage、资源、同步、tiling 和性能方案
  -> CANNBot 04：直调工程实现 kernel/host tiling，逐 Stage 定向验证
  -> CANNBot 05：基于直调工程完成全量精度、功能和性能验收
  -> CANNBot workflow complete
  -> 本仓适配：op_api/aclnn、Stable-ABI、Python API 和构建注册
  -> 本仓 ATK 交付与验收
  -> PR / CI
```

CANNBot 04 通过后进入 `validation`。CANNBot 05 在直调工程中完成 full 验收，通过后 workflow
更新为 `complete`，再进入本仓适配。ATK 资产生成、预检和 full 验收统一按
[`ATK 单算子验证工程`](../tests/atk/README.md)执行。

## 唯一标杆

CANNBot 02 生成的数学标杆在本仓直接交付为：

```text
tests/atk/<op>/reference.py
```

该文件就是 CANNBot 的唯一 `reference.py`，同时供 CANNBot 04/05 直调测试和本仓 ATK executor
导入。公式、状态更新和边界处理集中在该文件维护。

`reference.py` 应是纯 CPU/PyTorch 模块：

- 运行依赖限定为 CPU/PyTorch 和 Python 标准库；
- 以冻结接口接收输入和属性，返回完整输出 tuple；
- 内部计算精度、有效区域和边界语义与 golden contract 一致；
- 可以由直调测试和 ATK CPU 节点在不同进程中独立导入。

若当前 CANNBot 版本使用默认产物路径，通过无数学逻辑的路径转发或目标路径记录连接本仓位置，
可编辑实现仍集中在 `tests/atk/<op>/reference.py`。新建或重新进入 CANNBot 流程的算子按本约定
收敛，历史算子在后续进入流程时迁移。

## CANNBot 04：适配前直调验证

CANNBot 04 使用其直调工程完成快速反馈：host `main()` 负责 ACL 初始化、tiling、device 内存和
workspace，直接执行 `kernel<<<blockDim, ..., stream>>>`，拷回当前 Stage 或整 kernel 输出，
再使用同一 `reference.py` 和 CANNBot 精度策略比较。

每轮只运行失败用例、受影响 Stage 和最小边界集合：

1. 当前 Stage 实现后，运行从 Stage 0 到当前 Stage 的最小合法用例并比较中间输出。
2. 修复或优化只回归受影响 Stage、原失败 case、目标模型 shape 和必要边界。
3. 全部 Stage 拼接后，使用直调工程运行最小整 kernel 冒烟。
4. 每轮性能候选先过定向精度；只有最终候选进入 full 验收。

本阶段的调用边界由直调 host、原始 kernel、唯一 `reference.py` 和 CANNBot 精度比较入口组成。
仓库公开 API、适配层和 ATK 调用链在后续接入阶段启用。
直调精度失败按[直调精度失败定位](#直调精度失败定位)处理。

## CANNBot 05：算子测试与最终验收

CANNBot 05 继续使用直调 host 和原始 kernel，复用冻结的 `reference.py`、precision policy 和
CANNBot `compare_precision.py`，完成全量精度、功能、边界、异常、TilingKey/运行分支和性能验收。
性能以统一模型用例及 `msprof op_summary` 的 `Task Duration(us)` 为准。

性能未达标时保持 `validation`，每轮只改变一个主要变量，候选先通过精度再同条件比较。修改设计
假设返回 CANNBot 03，只修改实现返回 CANNBot 04；最终候选重新执行 fresh full 验收。所有要求
通过后，workflow 更新为 `complete`。
full 验收中的精度失败沿用[直调精度失败定位](#直调精度失败定位)流程。

## 本仓适配与交付衔接

CANNBot 五阶段完成后，按本仓文档完成算子定义与 InferShape 接入、op_api/aclnn、Stable-ABI、
Python wrapper、导出和构建注册。所有参数名称、顺序、类型、默认值和返回值必须与
`docs/api.md` 一致。

完成适配后，按[`ATK 单算子验证工程`](../tests/atk/README.md)准备 executor、YAML、正式用例资产
并执行预检和 full 验收。当前算子的输入限制、用例映射和验收结果记录在对应 ATK README。

## 产物和职责

| 环节 | 唯一产物或职责 |
| --- | --- |
| CANNBot 01 | `docs/api.md`、operator contract、目标架构 |
| CANNBot 02 | `tests/atk/<op>/reference.py`、definition、precision policy、golden contract |
| CANNBot 03 | `docs/design.md`、Stage/资源/同步/tiling/性能方案 |
| CANNBot 04 | `op_kernel`、host tiling、TilingData/TilingKey、直调验证证据 |
| CANNBot 05 | 直调工程的全量精度、功能、异常和性能证据，维护 workflow 状态 |
| 本仓适配 | op_api/aclnn、Stable-ABI、Python wrapper、导出和构建注册 |
| 本仓 ATK 交付 | 按[`ATK 单算子验证工程`](../tests/atk/README.md)完成资产生成、预检和 full 验收 |
| 本仓交付 | Example/ST、构建安装、PR 和 CI 材料 |

## 失败恢复

何时进入 ATK、测试资产如何交接，以及失败后返回哪个开发环节均由本工作流负责；
`tests/atk/README.md` 只定义 ATK 测试的准备、执行和通过标准。

| 失败证据 | 返回位置 |
| --- | --- |
| 接口或支持范围错误 | CANNBot 01 |
| 标杆、值域、有效区或数学语义错误 | CANNBot 02 |
| Stage、资源、同步、tiling 或性能方案错误 | CANNBot 03 |
| 直调 Stage 或整 kernel 结果错误 | CANNBot 04 |
| CANNBot 05 直调 full 失败 | 按证据返回 CANNBot 01--04；性能未达标保持 CANNBot 05 `validation` |
| 本仓整链路 smoke 失败 | 检查公开 API、Stable-ABI、op_api/aclnn、构建注册和安装结果 |
| smoke 通过但单 case ATK 失败 | 先检查 ATK executor、YAML、输入构造和数据转换；证据指向核心时返回相应 CANNBot 阶段 |
| ATK full 失败 | 适配或测试资产问题在本仓修复；核心问题返回相应 CANNBot 阶段，再重跑后续流程 |

CANNBot 性能达到目标前保持 `validation`，每轮改变一个主要变量，先做直调定向精度再同条件
测量。性能目标、本仓门禁和数学语义在两层验收期间保持固定。

## 附录

### 直调精度失败定位

以 `compare_precision.py` 的报告作为精度判定。精度失败时，保留失败输出的 NPU actual 和 CPU
golden，并使用 `ct viz` 查看误差空间分布。

可视化结论作为 Stage、布局、tail、mask 或同步问题的定位证据，记录到 `docs/validation.md`。
`ct viz` 用于问题定位，精度是否通过仍以 `compare_precision.py` 的报告为准。
